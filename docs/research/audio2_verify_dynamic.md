## Method (common to all items)

* Harness: `tools/trace/apu_probe.c` (own code, ~550 lines; links the pre-built mGBA fork `libmgba.so`; built by `tools/trace/build_apu_probe.sh`).  It boots the ROM for 300 frames
  (so HRAM, the bank-switch mirrors and the RAM vectors are the real ones), then takes the machine over: the CPU is parked in a `jr $` loop in WRAM, `IE = 0`, and the
  harness plays the role of the ROM's main loop.  Every frame it calls the ROM's own stub `Sound_FrameTick` (00:20A6, what the frame service 00:0392 calls once per frame);
  at scheduled frames it calls the other ROM stubs (`Sound_Init` 00:20A0, `Sound_PlayMusic` 00:20B2, `Sound_PlaySfx` 00:20AC, `Sound_SetTrackParam` 00:20D6 ...).  Only driver code runs.
* It single-steps the SM83 core (`core->step`) and records, with frame number, sequencer-tick counters (entries of 04:40F5 = music ticks tM, 04:40AC = sfx ticks tS) and PC:
  every CPU write to FF10-FF3F (`W`), every command start (the `call` of the stream reader at 04:45A7: DE = command address, `C`), StartNote (04:4A81, `N`), NoteGateExpired
  (04:4BFC, `G`), selected routine entries with the whole track and channel record (`Q`: WriteChannelPitch 04:4ECA, WriteChannelVolume 04:4F97, WriteChannelParams 04:4E4B,
  WriteChannelPan 04:4F4F, UpdateChannel 04:4C14, ComputeTrackOutput 04:4668, StartNote after the per-note instrument copy 04:4ABE, TickVibrato 04:45E6, the tail test 04:4D6A), CPU data reads of ROM (`--romread`) and of watched WRAM addresses (`--rwatch`),
  end-of-frame snapshots of the track / channel records (`--snap`), mGBA's own APU state per frame (`--apu`: envelope volume, length / playing flags, noise ratio and shift, wave level, NR51) and the audio samples it renders (`--audio`).
  The hook addresses are checked against the opcode bytes of the ROM at start-up.
* Independent decode: `tools/trace/audio2_macros.py` parses the macro source (`audio/music/*.asm`, `audio/sfx.asm`, `audio/music_pointers.asm`) with its own size table; it is
  cross-checked against the label addresses of the assembled `build/mobile_trainer.sym` (0 mismatches over all labels of all 29 + 1 files) and is not derived from
  `tools/audio_to_macros.py` or `tools/audio_driver_check.py` (neither was run or imported).
* Synthetic ROMs: private copies of the ROM (own file names, in the scratch directory only); streams are written into ROM banks that are entirely `$00` in the original (6, 7, 8, ...),
  and a song record (an id of `$1E`-`$28`, copies of song 1) or instrument records are patched in the copy.  The original ROM file was never opened for writing.
* Reproduce: `analysis/audio2_verify_dyn/reproduce.sh` (see the end of this document).

### V1.1  Command boundaries (doc sections 1, 3.2, 4.1, 4.2, 4.4, 9.1-9.2)

Method: all 59 distinct stream headers (ids `$01`-`$1D` through `Sound_PlayMusic`, `$29`-`$46` through `Sound_PlaySfx`; ids `$1E`-`$28` share the header of song 1) were played on mGBA until every

tick, and the track; `tools/trace/audio2_v11.py` compares these with the independent macro decode: first command = header word of the track; every address is a command of the decode in the right bank; the opcode byte
(or, for `sound_rs`, the last opcode >= `$BE` that the driver saw) is the one of the macro; the next address is exactly address + size / jump target / call target / return address (own call stack); the
tick delta is the wait value of a `sound_wait` and 0 for everything else; nothing is decoded after `sound_end`.  The comparator was mutation-tested (a wrong size of 3 `sound_instrument` and a wrong value of 3 `sound_wait 12` in the decode
produce `next` / `timing` violations and 39 "observed but not reachable" addresses).

Result (`analysis/audio2_verify_dyn/v11_summary.tsv`): **35 351 command executions, 59 headers, 152 tracks, 0 violations.**  11 823 distinct command addresses were decoded by the driver; the macro decode says exactly 11 823 are reachable
from the track starts (observed-not-reachable 0, reachable-not-observed 0).  The other 93 of the 11 916 commands (86 `sound_end` behind a final jump and 7 commands in the three codas at 05:4535, 05:4766, 05:52D7) are not executed by any

## Limits: what was NOT verified

* The 93 commands behind final jumps (86 `$B1`, 7 commands in three codas at 05:4535, 05:4766, 05:52D7) are never executed by any stream: their decode is checked only against the bytes/labels of the build.
* "No reader of header bytes +0/+1, header sets 1/2 and song-record byte +7": shown for the driver only (CPU data-read watch over the driver's executions); other ROM code (screens, the sound test, mail code) was neither run nor searched for such reads.  The same limit applies to the read watch of `+$1E`, `+$30`, `+$31`.
* Only what mGBA's APU model does is measured (register values, its internal envelope / length / ratio state, rendered samples).  Real-hardware behaviour (the zombie-mode quirks of NRx2 writes, wave RAM access while playing, DMG vs CGB differences) was not tested; the hardware frequency formula `131072 / (2048 - P)` is taken from the documentation (mGBA implements it; the measured frequencies agree with it).
* The harness replaces the ROM's main loop: the stubs are called from an idle loop with interrupts masked (`IE = 0`).  The re-entrancy guard of the stubs (`Bank4_GateEnter*`, the deferred tick path), the frame service `Sound_FrameService`, and any interaction with the rest of the ROM (a screen playing sounds while it draws) were not exercised.
* The "unused" envelope bits were swept on pulse 2 and noise (1 800 random notes each); the wave channel was checked for the NR32 mapping but not for these bits.  `Param` entry 5 with value 0 / `$80` (the word store path at 04:4915) and `Param` 0 with a value above `$80` were not examined in detail.
* Channel-level takeover between a music track and an effect (StartNote's priority test at 04:4B10), `Sound_FrameTick` arriving while another stub runs, and the behaviour of the 11 ids `$1E`-`$28` (copies of song 1, not used by any caller found) were not tested; the labels/ids were checked statically only.
* Section 9's claims about `tools/audio_driver_check.py` itself (5 867 + 5 956 commands executed, 300 000 commands run) were not reproduced by running that script; the equivalent figures here are 11 823 distinct / 35 351 executed commands on mGBA.
* The mGBA run models a CGB; the ROM is a CGB cartridge (the boot A register was set to `$11`), the DMG/AGB models were not tried.

## Additional observations (not claims of the note)

* Songs `$18` and `$1B` are one note followed by `$B1`: the track ends in the tick in which the note starts, so `UpdateChannel` silences the channel at once and the "song" makes no sound (frame 2: NRx2 `$08`, NRx4 `$80`, twice).
* For a pitch byte of a per-note-mode note beyond the 112 records (pitch + add + `$40` >= `$70`) the driver reads the bytes that follow the table (wave patterns, then the song records) as an instrument: there is no bound.
* A `$B5` loop with count 0 never leaves; `$B3` beyond depth 5 ends the track silently (no return, no `$B1`).
* The noise "pitch" is not monotonic: above x = `$4C` it cycles through four very high frequencies (NR43 `$08`-`$0B`); the data uses x up to `$64`.
* The ROM's own callers: `Sound_PlaySfx` is called with ids `$29`-`$46` (no `$37` as a literal) and with `$48` only in the unreferenced `engine/unreferenced/page_list_prototype.asm` (l.626, 1904); the driver ignores `$47` and above (nothing starts), so that call would be silent.  `Sound_PlayMusic*` literals cover `$01`-`$1D` except `$19` (computed ids not followed).
* Fade-out (`Sound_StartFadeOut`, A = 1) lowers `+$16` by 4 per tick from `$40` to `$00` and then pauses the music (track flags `$C0` -> `$40`), at which point `PlayMusicOrResume` of the same id resumes at the same stream pointer.

`apu_probe --rom FILE --out LOG [--boot N] [--frames N] [--call F:NAME[:regs]]... [--poke F:ADDR=hh,..]... [--ev wcngejtx] [--q PVBAUKLXZSIYD] [--snap] [--apu] [--audio RAW] [--romread FILE] [--rwatch ADDR,..] [--stop-loops K]`.
`analysis/audio2_verify_dyn/samples/` holds three raw event logs (songs `$29`, `$2C` and `$18`) as examples of the format.
